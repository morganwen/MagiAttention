# Magi-DSA 设计

这份文档讲清楚一件事：DeepSeek 那套稀疏注意力，怎么在 Magi 的上下文并行里跑起来，
而且跑得均匀。读它不需要先懂注意力的实现细节，只需要知道注意力是"每个 Query 去看
一批 Key，加权求和"。

## 稀疏注意力长什么样

一个标准的注意力层里，第 i 个 Query 要看它前面所有的 Key。序列长到 128k，这就是
128k 次比较，代价随长度平方增长。稀疏注意力的想法是：绝大多数 Key 对结果没有贡献，
不如只看一小部分。

Magi-DSA 里每个 Query 看三样东西：

- 一个滑动窗口，就是它前面最近的 128 个 token，逐 token 精确保留。
- 一串压缩块。每 ratio 个连续 token 被一个小网络压成一行，Query 看它前面所有的
  压缩块。压缩块是"远处的粗略摘要"。
- 一批被挑出来的远处 token。挑选由一个叫 Indexer 的小模型完成，它给每个候选打分，
  取分数最高的 1024 个。

层与层之间只有 ratio 不同，模型里两种层交替出现：

- ratio 等于 4 的层压得很细，叫 CSA。它带 Indexer，会做打分和挑选，所以还要额外算
  一份给 Indexer 用的压缩表示，并且训练时要让 Indexer 的打分去逼近真实注意力的分布，
  这就是那个 KL 损失。
- ratio 等于 128 的层压得很粗，叫 HCA。它没有 Indexer，每个 Query 就看窗口加上全部
  压缩块，不做挑选。

这两类层共用同一套数据布局，因为它们在同一个模型里前后相接。

## Magi 提供了什么

Magi 是为长序列的上下文并行做的。序列被切开分给多张卡，每张卡只持有一段 Query，
但注意力要求每个 Query 能看到它前面的全部 Key，这些 Key 散落在别的卡上。Magi 把这
件事抽象成两个动作：

- group-cast，把本卡产出的行发给需要它们的卡。
- group-reduce，反向时把各卡算出的梯度按行加回产出方。

关键在于这两个动作的输入是区间，不是逐行的索引表。一段连续的行用一个起止点描述，
计划的大小取决于分片数量而不是 token 数量。128k 序列切 8 张卡，计划里只有几十个
区间，不是十几万行索引。

Magi-DSA 只负责说清楚"我产出哪些行、谁需要这些行"，搬运本身完全交给 Magi。这个扩展
里没有自己的通信实现，没有逐行的收发表，也没有任何可训练参数——权重全部属于模型，
以回调的形式传进来。

## 上下文并行的难点

### 按 token 数平分是不均匀的

因为 causal mask，第 i 个 Query 要看 i 个 Key，工作量随位置线性增长。把 128k 序列
按 token 数平均切成 8 段，最后一段的计算量是第一段的 15 倍。等于 7 张卡等 1 张卡。

真正需要配平的是"每张卡的注意力面积"，也就是被激活的 Query-Key 对的总数，而不是
token 数。对一段从 u 到 v 的连续 Query，这个面积是一个梯形：

```text
causal_area([u, v)) = (u + 1 + v) * (v - u) / 2
```

再加上 varlen。训练数据是把长短不一的样本拼成一条长序列，样本之间互相看不见。一条
128k 的序列可能由几十个样本组成，长度从几百到几万。每个样本内部各自是一个三角形，
整条序列的工作量分布是一串大小不一的三角形。

### zigzag 为什么不够

zigzag 是常见的做法：把序列切成 2 倍卡数的块，每张卡拿一个靠前的块和一个靠后的块，
一头轻一头重，加起来就平了。

它成立的前提很强：

- 整条序列是一个样本，一个完整的三角形。varlen 下每个样本都得单独 zigzag。
- 样本长度要能被 2 倍卡数整除。除不尽就要补齐，补出来的 token 是纯浪费，样本越碎
  浪费越多。
- mask 必须是纯 causal。一旦引入滑动窗口或者别的结构，工作量就不再是干净的三角形，
  一头一尾配对的假设不再成立。

Magi-DSA 面对的正是这三条都不满足的情况。所以要换一种分法。

### 于是有两个具体问题要解决

一个是补齐。任何要求"每张卡拿到整齐块数"的方案都会产生补齐的 token，它们不参与
任何有效计算，却要占显存、占带宽、占算力。

另一个是通信。Query 分散之后，每张卡都需要别的卡产出的 Key，这是一次全体对全体的
交换。交换的量不小，而且不能让它白白占着时间。

## 负载均衡怎么做

### Magi 通用的分发算法

Magi 自带的分发算法是这样工作的：

- 把整条拼接后的序列切成固定大小的 chunk，默认 512 个 token 一块。chunk 的边界不需要
  对齐样本边界。
- 对每个 chunk，算出它在所有样本上的注意力面积之和，作为这个 chunk 的代价。
- 用一个最小堆做贪心分配：每次把最重的 chunk 给当前最轻的卡。
- 约束每张卡拿到的 chunk 数量最多相差一个。

结果是各卡的注意力面积接近，而不是 token 数接近。因为 chunk 不必对齐样本边界，也
不要求每卡块数完全相同，所以不需要补齐。一张卡最后拿到的是若干段不连续的 Query
区间，每段落在某个样本内部。

chunk 的大小会按序列长度自动收缩，保证卡数多、序列短的时候仍然有足够多的块可分：

```text
resolved_chunk_size = min(
    configured_chunk_size,
    ceil(total_tokens / (min_chunks_per_rank * cp_size)),
)
```

这个代价函数只看 causal 面积，跟 ratio 无关。这是有意的：CSA 和 HCA 必须得到完全
一样的布局，否则相邻两层之间就要重新搬一次 Query。

### 为 DSA 补上的部分

通用算法管的是 Query 怎么分。DSA 多出来一样东西：压缩块。每 ratio 个连续 token 压成
一行，这一行由谁来算，需要额外定规矩。

规矩有两条：

- 一个压缩块由持有它最后一个 token 的那张卡产出。不能是第一个 token，因为压缩要读
  完整个块才能算。按最后一个 token 归属，等价于块的编号取它结束位置除以 ratio 向下
  取整。这条保证每个块恰好有一个生产者，否则反向时同一份梯度会被累加两次。
- 一段压缩块区间不能横跨样本。下游是从区间的起点反推它属于哪个样本的，跨了样本这个
  反推就是错的。所以合并区间时按样本分组，样本边界处强制断开。

CSA 还要多产出一份给 Indexer 用的压缩表示，规矩完全一样，只是数据宽度不同。

## 通信是一次全体对全体的交换

数据搬运一共五条路由，每条都是同一个形状：一批本卡产出的行，发给需要它们的卡。

- TOKEN_LAYOUT，把原始的 hidden 行搬到均衡后的 Query 布局上。整个模型只做一次，
  不是每层都做。
- OVERLAP_X，把压缩要读的那些 hidden 行送给压缩块的生产者。
- WINDOW_KV，把滑动窗口要看的 Key 送给需要它们的 Query 持有方。
- COMPRESSED_KV，把压缩块的结果发给所有要看它的卡。
- COMPRESSED_KI，CSA 专用，把 Indexer 那份压缩结果发出去。

这五条落到底层都是一次变长的全体对全体交换。它和 MoE 的专家并行用的是同一类通信：
每张卡发给每张卡的数据量都不一样，事先要交换长度，然后一次 all2all-v 把数据换完，
两头各配一次按区间的收集和散射。熟悉专家并行实现的人可以直接套用那套心智模型。

有一点不同，而且这点很重要。专家并行的路由是运行时由门控网络决定的，每一步都不一样,
所以每一步都要先交换一轮长度信息。Magi-DSA 的路由完全由序列长度和样本切分决定，在
计划阶段就能算出来，而且每张卡各自算出的结果逐位相同。所以运行时不需要任何元数据
交换，也不需要 object 类型的集合通信，直接进数据面。计划本身是纯函数，同样的输入
在每张卡上得到同样的输出，不需要谁来广播。

### local 和 remote

布局做完之后，本卡的 Query 就固定了，DSA 内部不再移动 Query。剩下的只有 Key 从哪来
的区别：

- 本卡自己产出的 Key 是 local。
- 别的卡产出、需要取回来的是 remote。

这个区别不需要单独的表来记录。一条路由天然同时覆盖两者，local 的那部分在 all2all 里
就是自己发给自己。单卡运行时路由退化成一次本地的区间收集，反向退化成一次本地的区间
累加，代码路径是同一条。

## 计算和通信怎么重叠

通信的时间要用计算盖住，否则就是纯粹的等待。做法是把每条路由拆成"发起"和"等待"两步，
中间塞进不依赖这条路由的计算。

正向的安排是：

- 先发起 WINDOW_KV 和 OVERLAP_X，然后去算 Indexer 的投影。投影只用本卡的 hidden 行，
  跟这两条路由无关，所以能盖住它们。
- 等到 OVERLAP_X 回来，取出压缩要读的行，先跑 Indexer 的压缩并发起 COMPRESSED_KI，
  再跑主压缩并发起 COMPRESSED_KV。两个压缩互不依赖，后一个盖住前一条路由。
- 等 COMPRESSED_KV 落地，再做打分和挑选，最后把窗口和压缩拼成一个 KV 库做稀疏注意力。

这里有一处是特意不重叠的。打分用的是一个很吃 SM 的 cuDNN kernel，让 COMPRESSED_KV
在它底下跑，实测反而更慢：省下的通信暴露只有零点一几毫秒，打分核却慢了百分之三。
更麻烦的是慢多少取决于这张卡摊到多少通信量，于是一个本来均衡的切分会在 profile 上
显示成不均衡。所以这条路由宁可等它落地。重叠是手段不是目的，代价大于收益就不做。

反向的顺序是正向的镜像，但可用来遮挡的计算少得多，所以更需要精心排。反向必须由
调度自己驱动，而不是交给自动微分：自动微分只保证依赖正确，不保证发起和等待落在
我们想要的位置。所以每个模型回调都跑在一份分离出来的子图上，反向时由调度按程序
顺序逐个驱动。反向的顺序是：

- 先做输出的逆旋转位置编码，再做注意力和 KL 的反向。COMPRESSED_KI 的反向路由在这一步
  内部发起，被稀疏注意力的反向盖住。
- 拿到 KV 库的梯度，切成窗口部分和压缩部分，先发起 COMPRESSED_KV 的反向路由。它在
  关键路径上，主压缩器的反向要等它，所以让它先走、先拿满带宽。
- 跑 Indexer 压缩器的反向，盖住 COMPRESSED_KV。
- 等 COMPRESSED_KV 回来，跑主压缩器的反向，把梯度散射回 OVERLAP_X 的行上，然后发起
  OVERLAP_X 和 WINDOW_KV 的反向路由。窗口那条最后才等，所以放到这里发，不跟关键
  路径抢带宽。
- 最后跑 Indexer 投影的反向。这是唯一还剩下的、不依赖任何路由的计算，用它同时盖住
  上面两条。
- 收尾时等 WINDOW_KV 和 OVERLAP_X。

HCA 没有 Indexer，也就没有任何与路由无关的计算可用。它的三条路由中，COMPRESSED_KV
的结果是主压缩器反向的输入，OVERLAP_X 又消费主压缩器反向的输出，两条都卡在依赖上，
只有 WINDOW_KV 能被盖住。这是结构决定的，不是排布没排好。

## 两条必须守住的规则

一条是：一张卡发起的集合通信次数，绝不能取决于它本地的数据。

举个真实踩过的坑。有的卡在某一步恰好不产出任何压缩块，如果这时候图省事直接返回一个
空张量，这张卡的这条路径就从计算图上断了，反向时它会少发起一次通信。别的卡还在发，
于是整组卡永远等下去。正确做法是让它照样走完整条路径，只不过索引是空的。宁可发一次
零长度的通信，也不能让通信次数随数据变化。

另一条是：一个压缩块只能有一个生产者。多一个就会多累加一份梯度，而且这种错误在
单卡上完全看不出来。

## 这个扩展不拥有什么

这些是刻意写出来的，因为每一条都曾经被重复实现过一次：

- 没有自己的全体对全体数据面。路由就是 group-cast，它的反向就是对称的 group-reduce。
- 没有逐行的收发表。路由是区间，计划的大小取决于分片数量而不是 token 数量。
- 没有自己的收集或散射内核。重复行的收集用 index_select，前缀收集用 Magi 的区间算子。
- 没有可训练参数。所有权重属于模型，以回调形式传进来。
- 没有 object 类型的集合通信。计划是纯函数，每张卡自己重算一份完全相同的。
- 没有可选的布局策略。只有一种，就是上面那个结构均衡。
